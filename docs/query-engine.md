# 分散クエリ実行層の方針

状態：実装済み。互換性の結果は [sql-language.md](./sql-language.md) にある
作成日：2026-11-06

## 結論

`shardKey` の指定なしで普通の SQL が動くように、シャードの外側に実行層を足す。
全面的な自作はせず、分散プランナだけを自作し、実行はシャードも Worker も SQLite に任せる。

| 部品 | 決定 |
|---|---|
| シャード内の実行 | SQLite のまま |
| Worker 内の実行 | sql.js (SQLite の WASM ビルド) で元の SQL を実行する |
| パーサ | `sql-parser-cst` の SQLite 方言 |
| プランナ | 自作。押し下げは下記の安全規則に従う |
| `SHARD KEY` | 任意。省略時は PRIMARY KEY の先頭列のハッシュ |
| 複数シャードの UPDATE、DELETE | 明示した文だけ実行する。黙って変換しない |

式の評価を自作しないのは、同じ SQL が 1 シャードと複数シャードで黙って違う結果を返すのを避けるためである。
直近で見つかった「黙って間違う」バグは、Worker 側で SQLite の意味を再実装していたことが原因だった。
WASM で元の SQL を実行すれば、この種類のバグは起きにくくなる。

## 実測した事実

| 項目 | 結果 |
|---|---|
| sql.js 1.13 (SQLite 3.49.1) | workerd で動く。bundle 約 726 KB、初回の初期化 74 ms |
| wa-sqlite 1.0 (SQLite 3.44.0) | workerd で動く |
| 公式の `@sqlite.org/sqlite-wasm` | 動かない。起動時に wasm を実行時生成するため禁止される |
| 10 万行の投入 | 約 100 ms |
| 10 万行の GROUP BY、DISTINCT、窓関数 | 20〜34 ms |
| 10 万行どうしの PK JOIN | 13 ms |
| sql.js の FTS5 | 含まれていない |

パーサを 23 の構文で比べた結果、`sql-parser-cst` は 21 件を通した。
`node-sql-parser` は 14 件で、ON CONFLICT、UPDATE FROM、`OVER (ORDER BY ...)` もこの差に含まれる。
代償はサイズ (627 KB) と解析時間 (1 文 368 µs、`node-sql-parser` は 80 µs) である。
文法から自作のパーサを生成する必要はなくなった。

## 押し下げの安全規則

元の SQL をそのまま再実行しても、シャードへ押し下げる条件を誤ると結果が変わる。
次の例では、`b.x IS NULL` を b の走査へ押し下げると `x = 5` の行が届かず、a の行が NULL で補われて条件を通るので、結果が増える。

```sql
SELECT a.* FROM a LEFT JOIN b ON a.id = b.id WHERE b.x IS NULL;
```

そこで次の条件を満たすものだけを押し下げる。

- WHERE の条件は、参照する表が 1 つで、その表の全列が NULL のとき偽か NULL になるものに限る。
- ON の条件は、内部結合なら押せる。外部結合は NULL で補われる側へだけ押せる。
- OR で他の表を含むもの、相関サブクエリの中のもの、非決定的な関数は押さない。
- `LIMIT` と `ORDER BY` は、Top-N の演算子ができるまで押さない。

FTS5 の `MATCH` は WASM で再実行できないので、押し下げを必須にする。
押し下げられない文は拒否する。

## 読み取りの一貫性

各シャードから同じ `T` で行を集める。
Serializable の検証には、WASM の結果ではなく、各シャードへ押し下げた述語を read span として記録する。
結果は取得した行の関数なので、これで足りる。
述語を直近 write の索引で照合できない場合は表単位の照合に落ち、偽の abort が増える。
これが起きるのは読み書き取引が scatter するときだけである。

## 複数シャードの UPDATE と DELETE

「読んでから取引で書く」へ黙って変換しても Serializable にはならない。
`T` 以降に述語を満たすようになった行 (phantom) が見えないからである。
防ぐには走査した全シャードを読み取り専用の参加者にする必要があり、参加者数が fan-out の段差に当たる。
write set の 1 MB を超えると分割するしかなく、その時点で文の原子性は失われる。

そこで TiDB の非取引 DML と同じく、明示した文だけを実行する。
1,000 行かつ 8 シャード以内なら 1 取引で実行し、超えたら分割して進捗を返す。

## SHARD KEY の既定

PRIMARY KEY 全体のハッシュにすると、複合 PK `(tenant_id, id)` の `WHERE tenant_id = ?` が全シャードへ飛ぶ。
既定は PK の先頭列のハッシュとする。

ハッシュを range より優先するのは、連番の PK が range では末尾の 1 シャードに集中し、書き込みが約 950/s で止まるからである。
範囲検索を失う代償は、scatter と行予算で受ける。

shard key を後から変えるには、表の作り直しが要る。
pull 移動の単位は旧キーのグループで、新キーでは行の行き先がグループを跨ぐからである。

## 検討して捨てた案

| 案 | 捨てた理由 |
|---|---|
| 実行エンジンの全面自作 | 式の意味のずれで黙って間違う。シャード内の仕組みも SQLite に依存している |
| DataFusion の WASM | 10 MB 級で、方言が Postgres 寄り。シャードと結果が一致しない |
| 実行専用の DO | シャードと同じ上限があり、13 ms の追加の往復がかかる |
| Container で実行 | cold start が 1〜3 秒で、分析の層と重なる |
| シャード間の shuffle join | DO からの fan-out も同じ段差に当たり、データが 2 回動く |

## 実装で変えた点

方針を実装する過程で、次の点を変えた。

**複数シャードの UPDATE と DELETE**：明示を要求せず、既定で実行する。行を Worker の SQLite に集めて文を実行し、変更行を取引で確定する。走査した全シャードを参加者にするので Serializable を保つ。行数の上限を超えるとエラーになる。

**trigger**：Worker の SQLite で発火させる。

**表の見落とし**：手書きの解析に頼らず、実行の前に `EXPLAIN` で本物のプランナが開く表を確かめる。

**読み取りの時刻**：複数シャードの読み取りは対象シャードの時計の最大値を T にする。取引は読み取りの途中で T を進められる (read refresh)。

**高速経路**：部分集約と Top-N は WHERE の全条件をシャードへ押せるときだけ使う。条件が残ると結果が誤るからである。

## 未解決の点

**大きな読み取りの干渉**：シャードは 1 スレッドなので、大きな読み取りはその間の書き込みを止める。行の上限 (20 万行) はメモリからの推定で、OLTP に混ぜて安全な値は本番の負荷で測る必要がある。

**SQLite の版の差**：sql.js は 3.49.1 で、DO の SQLite の版は `sqlite_version()` が禁止されていて読めない。本番で `select1` は一致したが、全機能の一致は確かめていない。

**8 シャードを超える scatter**：fan-out の階層化は未実装である。

**semijoin**：結合の相手を絞る最適化は未実装で、シャードを跨ぐ JOIN は押し下げた条件以外で行を減らせない。
