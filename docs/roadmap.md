# 目標からの逆算と次の作業

状態：作業中
作成日：2026-11-09

## 目標と達成の定義

目標は、Cloudflare の上で SQLite 互換の、TiDB に倣って水平にスケールする NewSQL を作ることである。
達成を 2 段階で定義する。

| 段階 | 条件 |
|---|---|
| A. 自分のアプリで本番運用できる | `@libsql/client` や Drizzle のアプリを接続先だけ変えて 1 か月動かし、データの消失がない。増設、DO の再起動、コードの更新を跨いで手作業が要らない。月額が予測でき、誤った `DROP` から全シャードを同じ時点へ戻せる |
| B. 他人に勧められる | A に加え、複数の DB をトークンで分離できる。文の実行場所と競合率が利用者に見え、エクスポートとアップグレードの手順がある |

スループットが台数に比例して伸びることは 64 シャードまで確かめたので、達成したものとして扱う。

## 現状の抜け

次はコードと計測で確かめた。

| 抜け | 影響 |
|---|---|
| `__log` と `__txn` を消す処理がない (対応済み) | シャードは起動のたびに `__log` を全件読む。書き込み数に比例して起動時間とメモリが伸びる |
| `overloaded` が常に 0 (対応済み、条件を削除) | 過負荷による増設の条件が成立しない |
| `protocol_version` がない | 新旧コードの共存を `immediate` のデプロイで避けているだけである |
| 書き込み 1 回の課金が約 7 行 (対応済み、2 行) | D1 の約 6 倍の単価になる (下記) |
| 失敗の内訳が残らない | 本番の追試で出た約 2,000 件の失敗を追えない |

## 費用

### 内訳

ローカルの workerd で、課金と同じ行数を文の種類ごとに数えた (`ROWCOST=1 npx vitest run test/rowcost.test.ts`)。

| 操作 | 課金行 | 内訳 |
|---|---|---|
| 主キーでの読み取り | 0 | |
| 1 行の UPDATE (autocommit) | 7 | 下書き実行 4 (本体 1、捕捉 2、`__cap_on` 1)、適用 1、`__log` 2 |
| 1 行の INSERT (autocommit) | 8 | 同上 |
| 同じシャードの読みと UPDATE の取引 | 7.1 | 同上 |
| 2 シャードの UPDATE の取引 | 20.8 | intent と `__txn` が加わる |
| グローバル UNIQUE index のある表への INSERT | 19.2 | index の行と 2PC が加わる |

本番の追試では、行書き込み 970 万行に対して書き込みが 139 万回で、1 回あたり 7.0 行だった。
ローカルの数え方と一致するので、ROLLBACK した書き込みも課金されると判断した。

同じ方法で SQLite の基本操作も測った。

| 操作 | 課金行 |
|---|---|
| 主キーと rowid を持つ表への INSERT | 2 / 行 |
| `WITHOUT ROWID` の表、または `INTEGER PRIMARY KEY` の表への INSERT | 1 / 行 |
| DELETE | 1 / 行 |
| DROP TABLE | 0 |
| ROLLBACK した UPDATE | 1 / 行 |
| 1 行も変えなかった `INSERT OR IGNORE` | 0 |

DROP TABLE が 0 行であることは、変更ログの GC を世代の表の DROP にすれば GC の費用がかからないことを意味する。
ただし本番の課金で確かめたのは autocommit の UPDATE だけである。

### 削減案

| 案 | 効果 | 判断 |
|---|---|---|
| 行の変更を trigger ではなく読み取りで捕捉し、autocommit を下書きなしで直接実行する | 1 行の UPDATE が 7 行から 2 行になる | 採る。読み取りは書き込みの 1,000 分の 1 の単価である |
| `__log` を `WITHOUT ROWID` にする | 1 行減る | 採る |
| 変更ログを世代の表に分け、古い世代を DROP する | GC の削除が課金されない | 採る。GC と同時に入れる |
| 取引の文は捕捉だけ読み取りにする | 取引の下書き 4 行が 1 行になる | 採る |
| 複数の commit の変更ログを 1 行にまとめる (メモリで溜めてから書く) | 負荷が高いとき `__log` が 1 回あたり 1 行未満になる | 後で。応答は書き込みの確定まで待たせる必要があり、レイテンシと引き換えになる |
| 同じ行への更新をメモリで溜めて 1 回にまとめる | ホットな行でだけ効く | 後で。効く場面が狭い |
| DO の KV API の遅延書き込み | なし | 採らない。SQLite の DO の KV は内部の表に書かれ、行として課金される。書き込みのまとめはレイテンシと耐久性の往復を減らすだけである |
| Worker から DO への呼び出しを RPC の session にまとめる | DO のリクエスト ($0.15 / 100 万) が減る | 採る。呼び出しが返した stub への呼び出しは同じ session で、別に課金されない |
| クライアントから WebSocket (Hrana over WebSocket) で接続する | Worker のリクエスト ($0.30 / 100 万) が接続ごとになる | 採る。`@libsql/client` は `wss://` で対応している |

### 対応後の計測

捕捉の読み取り化、autocommit の直接実行、`WITHOUT ROWID` の世代の表を入れた後の値である。

| 操作 | 対応前 | 対応後 |
|---|---|---|
| 1 行の UPDATE (autocommit) | 7 | 2 |
| 1 行の INSERT (autocommit、複合主キー) | 8 | 3 |
| 同じシャードの読みと UPDATE の取引 | 7.1 | 3.05 |
| 2 シャードの UPDATE の取引 | 20.8 | 13.1 |
| グローバル UNIQUE index のある表への INSERT | 19.2 | 15.4 |

複合主キーの表は SQLite が rowid と主キーの index を持つので、INSERT は本体だけで 2 行になる。
2PC の取引は intent と `__txn` の行が残り、同じ取引を D1 で行う場合 (2 行) の 6 倍を超える。
`ROWCOST=1 npx vitest run test/rowcost.test.ts` が上限を検査する。

行の削減は書き込み費用の 9 割に効き、リクエストの削減は行を減らした後に効いてくる。

| 1 行の UPDATE 100 万回 | 行 | リクエスト | 合計 |
|---|---|---|---|
| 現状 | $7.0 | $0.48 | 約 $7.5 |
| 捕捉の読み取り化、`WITHOUT ROWID` | $2.0 | $0.48 | 約 $2.5 |
| さらに WebSocket と RPC session | $2.0 | ほぼ $0 | 約 $2.0 |
| さらに変更ログのまとめ書き (高負荷時) | 約 $1.1〜1.5 | ほぼ $0 | 約 $1.1〜1.5 |
| D1 (参考) | $1.0 | $0.30 | 約 $1.3 |

D1 との差は変更ログの 1 行で、これは過去時点の読み取り、競合の検出、移動、分析に使うので消せない。

形式モデルは、冒険的な設計を含む箇所にだけ足す。
取引記録の GC はこれに当たると判断し、`specs/m10_txn_record_gc.qnt` で確かめた。

実装は保持時間 (1 時間) の半分より古い取引の COMMIT を拒否する。
それ以外は実装とテストを優先する。

## 後回しにするもの

分析の経路 (DuckDB、R2、Container) は、目標の OLTP に必須ではない。
scatter の階層化、semijoin、本番でのスループットの追加計測も後にする。
Serializable の既定、行ロック、merge を作らないこと、4,096 スロットの固定は変えない。

## 増えすぎの検証についての訂正

本番の自動増設の計測は、応答が返ると次を送る負荷 (closed loop) だった。
台数が増えて応答が速くなると負荷も増えるので、閾値 (450/s) の近くに留まったまま増え続ける。
120 クライアント × 4 並列で応答 24 ms なら上限は約 2 万/s で、閾値で割ると約 44 シャードまで増えるのが正しい動作である。
33 シャードで止まらなかったことは、増えすぎの証拠にはならない。
止まることを確かめるには、一定レートの負荷 (open loop) で測る必要がある。

記録した判定を再生すると、応答時間 150 ms を単独で飽和とみなす判定は、1 シャードあたり 36〜95/s の負荷でも発火していた。
応答時間が閾値を超え、かつ負荷が閾値の 4 割 (180/s) 以上のときだけ飽和とみなすよう変えた (600 ms 以上は負荷によらない)。
4 割にしたのは、以前の本番で飽和したシャードの処理量が 200〜490/s まで落ちたからである。
再生では低負荷での発火が消え、33 シャードでも約 280/s で応答 169〜396 ms のシャードでは発火が残る。
これが本物の飽和か、一斉の問い合わせによる揺れかは、一定レートの負荷で測るまで分からない。

黒箱検査で、次の 3 つの不具合が本番で初めて見つかった。

1. DO の SQLite は複合 SELECT を 5 項までしか受け付けない (公式の制限表にない)。変更ログの view が 6 世代目で壊れた。
2. anchor が決着を送り損ねた intent は、読み手が来るまで参加者に残った。
3. 1 シャードで実行する利用者の 6 項以上の複合 SELECT が失敗していた。

いずれも直し、シミュレータの SQLite にも同じ制限を模して入れた。
