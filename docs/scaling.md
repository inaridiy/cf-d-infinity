# シャードの自動増設とストレージの設計

状態：中核を試作に実装し、本番で動作を確認した。全シャード復元と変更ログの GC は未実装
作成日：2026-11-06
前提：[design.md](./design.md)、[benchmarks.md](./benchmarks.md)、[specs/README.md](../specs/README.md)

## 結論

運用者の手作業なしにシャードを増やす機構を、次の 4 つで構成する。

| 要素 | 決定 |
|---|---|
| 範囲表 | 4,096 スロットに固定し、スロットを DO へ割り当てる。DO は 8 個から始める |
| 増設 | 所有権を先に子へ切り替えて負荷を移し、データは shard key の単位で後から移す |
| 判断 | シャードの metrics を Autoscaler DO が見て、Workflows で増設を起動する |
| 縮小 | merge は作らない。idle な DO の計算費用は Autoscaler の毎分 1 回の問い合わせだけなので、縮小は課金の上でほぼ自動で起きる |

範囲表のスロット数を固定するのは、増設を「スロットの所有権の移動」だけで表すためである。
ハッシュの切り方が変わらないので、行の所属先の計算は増設の前後で同じになる。

この機構で増えるのは、シャード単位の処理能力と容量である。
単一のホットな行と、1 シャードに収まらない単一の shard key の値は増設で解けず、後述の限界として残る。

## 所有権の移動

設計の当初案は「全範囲を fence し、コピーしてから切り替える」方式だった (`specs/m5_split_fence.qnt`)。
しかしこの方式は、コピーと通常処理が 1 スレッドを奪い合うので、負荷の高いシャードほど割れない。
増設が最も必要な場面で機能しないわけである。

そこで H-Store の Squall と同じ pull 型へ変える。
どちらも単一スレッドのパーティションを前提としているので、構造が合う。

1. Autoscaler が親 P に移すスロット集合 S の fence を指示し、P が永続化する。以後 P は S への読み書き、prepare、phase 2 を受けず、`NotOwner(C)` を返す。
2. Meta の範囲表を切り替える。この時点で負荷は子 C へ移る。
3. C は要求が来たグループ (同じ shard key の値を持つ全表の行) を P から pull する。背景でも P の本体を列挙して順に pull する。
4. pull を受けた P は `__moved(g, m, C)` を `sync()` で確定してから応答する。応答は行、`__ver`、intent を保ったまま 1 MB ごとに分割して送る。
5. C は `arrived(g) = m` を確定し、`HLC = max(HLC, m)` としてから、そのグループの要求を受ける。
6. 全グループの ack を受けたら P は S の行を DELETE する。`__moved` は変更ログの窓と PITR のために残す。

pull は冪等なので、P と C のどちらが再起動しても再送で済む。
グループの移動は P 側で原子的に確定するので、fence なしで切り替えても 2 重受理は起きない (モデルで確認した)。
連鎖した増設 (P から C、C から C2) でも `m` の順序は保たれる。

### 時刻 m の扱い

当初案は移動を時刻 `m` の取引として `__log` に残し、rollback-read で親子どちらでも読めるようにしていた。
Fable の検査はこの案を 2 箇所で破った。

子の undo が破れる例を示す。
親のグループ g に `w1` が `c = 1` で commit されている。
所有権の切り替えの前に `T = 1` を取った読み手が、切り替え後に子へ届く。
子は挿入の記録 (`m = 2`) を undo するので「行なし」を返すが、真の値は `w1` である。

親の undo も破れる。
移動の `m` と 2PC の `c` の順序が逆転するので、「`T < m` は親で読める」が成り立たないからである。

そこで移動は `__log` に載せず、版を保った物理移動とする。
`T < m` の読みには C が `ReadTooOld(m)` を返し、Worker が `T` を上げて読み直す。
書き手の `T < m` は abort する。
scatter も同じ規則で `T` を上げるので、重複も欠落も起きない。

`__ver` は保たれるので first-committer-wins の判定は正確である。
直近 write の索引は運ばず、C はグループの low-water を `m` にする。
`T < m` がすでに拒否されるので、偽陰性は生じない。

### 移動中の phase 2

もう 1 つの破れは、pull の応答が飛んでいる間の phase 2 である。
P が `__moved` を確定して応答を送った後、未解決の intent に `c` の phase 2 が届く。
ここで P が適用すると、C が受け取るスナップショットにはその書き込みがなく、書き込みが消える。

phase 2 と refresh は「intent がある DO」ではなく「`__moved` が示す DO」へ転送し、未到着なら anchor の alarm で再試行する。

## 増設の判断

Autoscaler DO が全シャードの metrics を集めて判断する。
平常時は Cron Trigger が毎分 1 回起こすだけで、閾値を超えたシャードか進行中の増設がある間だけ 5 秒の alarm で判断を続ける。
常に 5 秒周期で問い合わせると、負荷のないシャードも起きたままになり、Duration の課金が止まらないからである。
Autoscaler を起こすかどうかは `wrangler.jsonc` の `triggers.crons` で決まり、起動のための HTTP 呼び出しはない。
既定では割るべきシャードを記録するだけで、変数 `DINF_AUTOSCALE` を `split` にしたときだけ実際に割る。
増設は取り消せず、途中でやめる手順もないからである。
1 グループ (同じ shard key の行) は 1 回の RPC で運ぶので、16 MB を超えるグループは運べない。その場合はグループを名指しした誤りで止まる。
次の条件のいずれかが連続して成り立てば増設する。

| 条件 | 閾値 | 根拠 |
|---|---|---|
| 飽和 | metrics 要求の往復が 150 ms 以上で負荷が閾値の 4 割以上、または往復が 600 ms 以上 | 平常時は約 15 ms。待ち行列の長さを表すが、多数のシャードへの問い合わせでも揺れる |
| 書き込み | 450/s | 上限 950/s の 47%。pull に親のスレッドを残す |
| 読み取り | 1,150/s | 上限 2,300/s の 50% |
| サイズ | 1 GB | 移動の費用はサイズに比例するので早く割る |

飽和の条件は本番の失敗から加えた。
当初は処理量の閾値だけだったが、飽和したシャードの処理量は 200〜490/s に落ち、閾値を連続で超えなかった。
負荷が高いほど処理量が下がるので、処理量だけでは最も必要な場面で検知できない。
往復時間は待ち行列に並ぶ時間を含むので、飽和すると桁違いに伸びる。

クロスシャード取引の参加は、要求 2 回分として数える。
増設は同時に 4 件まで、同じ系列は 10 分空ける。
merge がないので、シャード数が振動することはない。

1 シャードの負荷の 50% 超が単一のグループに集中している場合は、増設しても解けない。
グループ内を表の境界で分けるか、運用者へ通知する。
単一の行が原因なら通知だけを行う。

ストレージの保護として、4 GB で書き込みを絞り、8 GB で INSERT を拒否する。
10 GB の上限に達してから増設を始めるわけにはいかない。
増設中も親は書き込めず、子へ移した分だけ容量が空くので、これらは増設が遅れたときの保険である。

## 初期のシャード数

DO の個数は `max(8, 予想 write/s ÷ 450, 予想サイズ ÷ 1 GB)` を 2 の冪へ切り上げる。
8 から始めるのは、fan-out が 7 前後まで 15 ms で済むからである。
当初案の 256 個は、scatter に 1 クエリあたり 256 回の DO 要求が要るので見送った。
クロスシャード率は `1 − 1/N` で、64 と 256 の差は 1.2 ポイントしかない。

8 個から増やすと、行は 4,096 個まで最大 9 回移動する。
1 回あたりの費用は書き込みと削除の行課金である。
大きくなると分かっている database は、初期値の式で最初から大きくするのがよい。

## ストレージの扱い

### 変更ログの GC

`__log` は世代テーブルに分け、R2 への flush と保持窓を過ぎた世代を `DROP TABLE` で捨てる。
ローカルの workerd では `DROP TABLE` の `rowsWritten` は 0 で、`DELETE` は 1 行ごとに計上された。
本番の課金は未確認である。

### 領域の回収

ローカルの workerd では、行を DELETE すると `databaseSize` は即座に減った。
`VACUUM` は使えないが、増設後に親の領域が戻るなら要らない。
本番でも同じかを確認する必要がある。

### 全シャード同時点の復元

PITR は DO ごとの機能で、各シャードを同じ時刻へ戻しても揃う保証がない。
当初案は PITR で `W` の直後へ戻し、変更ログで undo する方式だった。
しかし flush 済みの世代は DROP されているので before-image がなく、bookmark が `W` より前に落ちると補えない。

そこで redo 方式にする。
`specs/m7_restore.qnt` はこの手順を検査した。

1. 復元点 `W` を選ぶ。`W` は全シャードの flush 済みの時刻である。
2. 各シャードを `W − ε` を目標に PITR で戻す。bookmark が概算でも `W` を超えないようにするためである。
3. R2 の変更ログから `(bookmark, W]` を redo する。`W` 以下は flush 済みなので必ず存在する。
4. 未解決の intent は、anchor の決着が `c ≤ W` のものだけ適用する。
5. HLC を `W` 以上にする。範囲表は Meta の PITR で `W` の時点へ戻し、`W` より後に生まれた DO は捨てる。

消した DO は PITR できないので、30 日は `deleteAll` しない。
R2 の変更ログは外部バックアップも兼ねる。
anchor の `__txn` が復元点より古くなる場合があり、データは redo で戻るが `__txn` の不整合は残る。
復元後は `__txn` を参照しない手順を実装時に詰める必要がある。

### コールドデータ

全データを DO の料金で持つ問題は、この機構では解かない。
時系列の表を R2 へ退避する機能は別の設計とする。

## 縮小

merge は実装しない。
DO は使われなければ計算費用がかからないので、負荷が下がれば費用も自動で下がる。
ストレージの料金はデータ量で決まるので、シャード数には依存しない。
シャード数が残る弊害は scatter の幅だけである。
空になった DO は 30 日後に消す。

## 限界

増設で解けないものを、利用者に見える形で扱う。

**単一の行**：約 645 write/s で頭打ちになる。通知のみで、アプリ側でカウンタを分散してもらうしかない。

**単一の shard key の値**：1 シャードの容量 (書き込み約 950/s、10 GB) を超えると割れない。
範囲はハッシュで切るので、値の内部を切る手段がなく、表の境界で分けるのが限度である。
1 つの表が単体で容量を超える大口テナントは、より細かい shard key を選び直す必要がある。

**最大シャード数**：4,096 である。上限に達するのは書き込み約 390 万/s (実測の上限から計算)、または 4 TB 前後の水準で、スロット数を増やすには範囲表の移行が要る。

**バーストへの反応**：最初の検出は Cron の周期で最大約 1 分遅れ、判断にさらに数十秒かかり、1 回で処理能力は最大 2 倍までしか増えない。本番の実測では、シャードを 2 個から 8 個へ増やすのに約 50 秒かかった。瞬間的な突発には間に合わない。

**増えすぎ**：merge がないので、閾値が敏感だと台数が増え続ける。一定レートの負荷 (3,000 書き込み/s) では、8 シャードで止まり、その後 6 分増えなかった ([benchmarks.md](./benchmarks.md))。応答が返ると次を送る負荷では、台数とともに負荷も増えるので止まらない。

**移動中の全表読み**：scatter は移動が終わるまで `Migrating` で待たされる。増設が続くと scatter が通りにくくなる。

**巨大なグループ**：1 グループは 1 回の RPC で運ぶ。1 MB を超えるグループの分割転送は未実装である。

## 移動中の影響

切り替え直後は、未移動のグループへの最初の要求に pull の往復 (DO 間 RTT 約 13 ms とデータ転送) が乗る。
大きなグループでは待ちが長くなる。
`T` の古い取引は abort されて再実行される。

移動の速度は実測で 4.1 MB/s で、1 GB のシャードの増設には約 2 分かかる。
書き込み負荷をかけたままの移動では、処理量が約 4 割落ち、p99 が約 6 倍になった ([benchmarks.md](./benchmarks.md))。

モデルの誤りは結果の誤りになるので、実装時に反例を実コードのテストへ戻して確かめる。

## 残りの作業

範囲表、pull 型の移動、Autoscaler は試作に実装した。
残りは次のとおりである。

1. 増えすぎの抑制は、一定レートの負荷で止まることを確かめた。既存のシャードを子にした移動が本番で止まった仕組みと、移動のない区間で出た失敗の原因も調べる。
2. 変更ログの世代テーブルと R2 への flush。
3. 全シャード復元と、その復旧訓練。
4. 増設の手順を Workflows へ移す。今は Autoscaler DO が直接動かしている。
5. pull の転送速度の改善。並列化で 4.1 MB/s を上げられるかを確かめる。
