1. **The plan leaves query equivalence, public value fidelity, and recovery progress without sufficient protection.** These classes can survive correct ownership of all six invariants:

   | Class | Concrete example and evidence |
   |---|---|
   | SQL transformations change semantics despite correct spans | `AVG(x)` becomes shard-side `SUM(x)` plus `COUNT(x)`. With 1,025 rows containing `9007199254740991` on one shard, the integer sum overflows although SQLite’s original `AVG` can succeed. Every declared read span can be correct. See [plan.ts:594](packages/cf-d-infinity/src/sql/plan.ts:594). |
   | Values are corrupted before the invariant checks receive them | Hrana integer `"9007199254740993"` becomes JavaScript number `9007199254740992`. A perfect key encoder and replay checker downstream can agree about the already changed value. This also affects non-key columns. See [hrana.ts:56](packages/cf-d-infinity/src/client/hrana.ts:56). |
   | Safe protocols cannot make progress on admitted data | A shard-key group can accumulate beyond 16 MB through individually valid transactions. Split ownership switches before copying; `pull()` then refuses the group. Ordering DDL behind that split preserves safety while potentially blocking DDL indefinitely. See [autoscaler.ts:161](packages/cf-d-infinity/src/autoscaler.ts:161) and [core.ts:673](packages/cf-d-infinity/src/shard/core.ts:673). |
   | Prepare-time feasibility expires before application | An apply trial can succeed, then unrelated writes consume the remaining storage before phase 2. `finalize()` still needs space for table/index changes and the change log. Rollback does not reserve that space; the documented 10 GB limit remains relevant. See [core.ts:1820](packages/cf-d-infinity/src/shard/core.ts:1820) and [platform-facts.md:11](docs/platform-facts.md:11). |

   These are source-based examples, not newly reproduced defect reports. The missing distinction is between **correct validation**, **correct observable execution**, and **eventual recoverability**.

2. **Invariant 1: keep the conservative default, but make routing completeness part of the contract.** The Worker is the appropriate owner of SQL/route/span construction; the shard owns validation against changes and intents. Compilation checks the referenced table set, however, not whether all required rows reach the selected shards. [Db.tablesOf](packages/cf-d-infinity/src/client/db.ts:755) accepts the planner’s known tables; it does not verify its locality proof.

   The simpler boundary is one plan object that produces the scan SQL, destination set, and spans together—the existing [scanSpans](packages/cf-d-infinity/src/client/spans.ts:78) approach. Arbitrary pushed SQL needs an explicit, tested locality rule; otherwise gather complete inputs or reject it. Counting span-construction functions cannot establish this property.

   The public DO SQL interface exposes execution and cursors, with no authorizer or row-access hook in the [installed interface](packages/cf-d-infinity/node_modules/@cloudflare/workers-types/index.d.ts:3862). Consequently, the proposed mechanism remains a planner contract backed by testing, rather than runtime enforcement of actual reads.

3. **Invariants 2 and 3: the owners are appropriate, but the promises exceed what their proposed trials establish.**

   | Invariant | Assessment and simpler mechanism |
   |---|---|
   | **2 — committed transactions are applicable; owner: prepare** | Reusing the real apply kernel is right. Apply the same constraint/reservation rules to every writer, including direct autocommit. Extract a synchronous SQL-only kernel first: naïvely dry-running `applyAndLog()` also changes JavaScript state through `maxCommit`, `recent`, and pruning, which SQLite rollback cannot undo. See [core.ts:1593](packages/cf-d-infinity/src/shard/core.ts:1593). Keep the supported constraint domain deterministic and document why checking committed state plus outstanding intents suffices for that domain. Add admission headroom and conditional recovery guarantees; quarantine must preserve the committed decision and block unsafe access, never silently discard it. |
   | **3 — logged DDL executes everywhere; owner: Meta** | Validating both executable forms is right for syntax, engine differences, and generated internal DDL. Empty databases cannot establish applicability to populated databases. The later decision to retain data-dependent DDL therefore invalidates the original mechanism’s sufficiency. Existing tests explicitly demonstrate this distinction: [schema-failure.test.ts:50](packages/cf-d-infinity/test/schema-failure.test.ts:50). Either retain a durable prepare/apply/withdraw lifecycle, or use a write barrier for the supported populated-table changes. The invariant should distinguish a logged *operation attempt* from a published schema. |

   Synchronous rollback trials are feasible using the existing [rollback wrapper](packages/cf-d-infinity/src/shard/core.ts:1141) and [transactionSync adapter](packages/cf-d-infinity/src/worker.ts:98). Holding such a transaction open while contacting other objects is not feasible under [the documented synchronous callback restriction](docs/platform-facts.md:22). Space reservation and nondeterministic-constraint behavior were not verified against a live DO.

4. **Invariant 4: Meta should own admission and epochs; a shared log alone is insufficient.** A durable `begin/end` record prevents the check-then-start race only if every participant rejects stale or unauthorized operations. Today, split stages carry ranges and schema versions, without a reconfiguration operation identity: [autoscaler.ts:161](packages/cf-d-infinity/src/autoscaler.ts:161).

   Use a durable maintenance operation with an ID, epoch, participants, progress, and terminal outcome. Delayed `fence`, routing-switch, and completion messages must belong to that operation. Initially, one outstanding maintenance operation is simpler than concurrent admission rules.

   Execution need not all move into Meta: the autoscaler already persists pending split jobs and resumes them at [worker.ts:356](packages/cf-d-infinity/src/worker.ts:356). Meta can authorize and fence that driver. The combined model must include prepared/committed transactions, index publication, withdrawal, stale messages, and recovery progress—not merely DDL/split mutual exclusion. In particular, specify what releases the maintenance slot after an unmovable group or failed driver.

5. **Invariants 5 and 6 need stronger definitions before choosing their mechanisms.**

   | Invariant | Assessment and simpler mechanism |
   |---|---|
   | **5 — user SQL cannot access internals; owner: Worker compilation** | A user-only compilation database is useful, but successful compilation is not authorization. `sqlite_master` exists there, and `pragma_table_info('__txn')` compiles without the named table existing. Embedded metadata expressions can therefore compile against the shadow database and mean something different against a physical shard. The extractor considers only `OpenRead`/`OpenWrite` and excludes SQLite tables: [scratch.ts:82](packages/cf-d-infinity/src/sql/scratch.ts:82). Simpler: an explicit admission policy that confines metadata access to the user shadow database and rejects it inside pushed SQL. Keep trusted internal statements separate. |
   | **6 — one identity for rows and shard keys; owner: one module** | Centralization is right, but row identity and shard-key equivalence are different properties. Ordinary SQLite permits multiple NULL-containing values in a declared non-integer primary key. Encoding their declared key columns cannot distinguish those physical rows. The current implementation selects by `IS ?` and takes the first match: [rows.ts:50](packages/cf-d-infinity/src/shard/rows.ts:50). Simpler for alpha: require non-NULL declared keys, or preserve actual rowid identity where declared keys are insufficient. Specify the supported numeric domain too. |

   Both need fail-closed admission rules, not merely fewer helper functions. I did not execute the embedded-metadata scenario against workerd.

6. **All five detection tools can give false confidence; their generators are the important unfinished deliverable.**

   | Tool | False confidence | Required generator |
   |---|---|---|
   | **Span check** | Deleting *all* outside rows can hide cancelling dependencies: two outside counts can remain equal before and after deletion. Empty outside data also cannot reveal phantom dependencies. The implementation skips unstable results and databases exceeding 3,000 rows: [core.ts:1205](packages/cf-d-infinity/src/shard/core.ts:1205), [core.ts:1234](packages/cf-d-infinity/src/shard/core.ts:1234). | Generate pairs of states equal inside spans but independently insert, update, and delete outside subsets. Include absent-row witnesses, pending intents, overlays, aliases, correlated reads, and different shard placements. Report checked/skipped counts. |
   | **Apply dry-run / row-image round trip** | Reusing the same capture/encoding logic on both sides can reproduce the same mistake. A present-state trial says nothing about later resource availability. | Execute original SQL independently, then compare typed final rows, multiplicity, results, and constraint outcomes after capture/encode/restart/apply. Generate key moves, swaps, REPLACE/UPSERT, defaults, CHECKs, partial UNIQUEs, BLOBs, numeric boundaries, intent interleavings, and near-limit states. |
   | **Commit-order replay into SQLite** | Replaying supplied after-images certifies internal consistency rather than SQL semantics. Timestamp ordering alone also permits stale reads that violate the promised real-time guarantees. The current checker sees only successful recorded transactions; some uncertain outcomes are skipped at [history.test.ts:123](packages/cf-d-infinity/test/history.test.ts:123). | Retain original statements, parameters, intermediate observations, invocation/response order, and durable outcomes—including lost replies. Replay transaction-local writes correctly. Generate independent sessions, read-only transactions, failures followed by continued use, delayed phase 2, and reads excluding the anchor. |
   | **Key-identity check** | Comparing outputs built with production `encode`/`fold` can share the implementation’s error; sets can hide duplicate physical rows. The existing index checker does both: [invariants.ts:54](packages/cf-d-infinity/test/invariants.ts:54). | Generate schemas and typed values together. Check storage normalization, query-parameter equality, uniqueness, physical row multiplicity, and routing independently in SQLite. Include NULLs, INTEGER/REAL distinctions, TEXT affinity, BLOBs, composite keys, and precision boundaries. |
   | **Deterministic scheduler** | Determinism makes failures reproducible; it does not make the simulated platform accurate. `sync()` currently just sleeps, and restart retains the same SQLite database: [sim.ts:78](packages/cf-d-infinity/test/sim.ts:78), [sim.ts:192](packages/cf-d-infinity/test/sim.ts:192). | Control request/reply delivery, durable confirmation, loss of unconfirmed writes, output gates, timers, alarms, randomness, restarts, and mixed versions. Generate fault prefixes followed by fair recovery. Timer injection alone cannot test durability-order regressions. |

   Cross these generators. Separate SQL fuzzing and concurrency fuzzing will continue missing their intersections. Also reconcile simulator limits: [sim.ts:15](packages/cf-d-infinity/test/sim.ts:15) still says 2 MB while [platform-facts.md:20](docs/platform-facts.md:20) says 8 MB.

7. **Keep the cuts, but narrow unnecessary restrictions and add missing admission limits.** The later note already supersedes two initial choices: non-unique indexes become local, UNIQUE lookup routing returns, and serializability stays. Those decisions should replace the earlier baseline rather than remain competing instructions: [plan:151](.agents/execplans/2026-11-10-foundation-rework.md:151).

   A blanket ban on non-BINARY *index* columns is unnecessary for local indexes; SQLite handles those comparisons. Restrict the ban to identity/routing obligations until verified. The existing local NOCASE UNIQUE test supports this narrower cut: [committed-applies.test.ts:54](packages/cf-d-infinity/test/committed-applies.test.ts:54).

   Missing cuts or explicit contracts are unsafe integers, insufficiently unique declared keys, nondeterministic constraints, connection-changing PRAGMAs that cannot persist, and data that cannot be moved by the current transfer protocol. For groups, either enforce movability before ownership changes or implement chunked transfer.

   Retaining populated `CREATE UNIQUE INDEX` for migration tools is reasonable. Retaining all data-dependent DDL on that rationale is broader than necessary. Nor does that one feature establish migration compatibility: transaction-contained DDL is already refused at [db.ts:471](packages/cf-d-infinity/src/client/db.ts:471). Use actual generated migration scripts to choose that surface.

8. **Snapshot isolation is the wrong general escape from conservative-span conflicts.** It changes an application-visible guarantee and admits write skew—the repository already has the relevant [counterexample](packages/cf-d-infinity/test/counterexamples.test.ts:76). It also does not remove UNIQUE reservation, atomic visibility, or recovery obligations.

   Preserve serializability and measure abort reasons, retries, completion latency, and billed rows per successful transaction under realistic tenant skew. Add narrowing rules only at the shared plan/span boundary with independent differential checks. The current UNIQUE rule already demonstrates this approach: [spans.ts:59](packages/cf-d-infinity/src/client/spans.ts:59). Use short transactions, existing pessimistic modes, and admission/backpressure for genuinely hot contention. If SI is offered later, make it explicit and separately specified. The latest note’s decision to retain serializability is sound.

9. **The exit criterion is measurable only after substantial clarification, and is currently insufficient.** The [four criteria](.agents/execplans/2026-11-10-foundation-rework.md:17) permit several vacuous successes:

   - Mutation success depends on a frozen inventory, severity classification, seed budget, and treatment of mutants made unreachable by cuts.
   - “Restore one feature and get an error” can pass simply because admission still rejects that feature.
   - “No new failure class” permits recurring known failures and depends on subjective classification.
   - One helper function can faithfully centralize an incorrect rule.

   Require zero safety violations, minimum successful execution coverage for each supported category, bounded recovery after faults stop, and explicit limits on unexplained rejection/abort rates. Add held-out schema/SQL combinations and higher-order cases such as DDL × split × delayed phase 2 × restart.

   The current differential harness treats `unsupported:` as success and skips reference execution at [diff.ts:54](packages/cf-d-infinity/test/diff.ts:54). Track acceptance coverage and verify rejection leaves observable state unchanged. Keep two weeks of burn-in, but report operations, seeds, exercised combinations, skips, and recovery outcomes alongside elapsed time.

10. **I would change the implementation sequence and make a few stronger early simplifications.** Build the independent SQL/API replay harness and deterministic durability scheduler before restoring UNIQUE lookup routing. The latest [next-step order](.agents/execplans/2026-11-10-foundation-rework.md:182) currently puts routing implementation first.

    Then establish three boundaries: admitted SQL/value semantics; a synchronous apply kernel with side effects separated from trials; and durable maintenance admission with operation epochs. Use complete gather execution as the comparison baseline for optimizations. For initially supported populated-table DDL, consider a write barrier instead of preserving broad online-DDL behavior.

    The costs are explicit: more upfront harness work, temporary scatter/gather overhead, billed writes from rollback trials, maintenance write pauses, and reduced SQLite compatibility where values or keys are rejected. These costs are easier to measure than the confidence supplied by another green review round.
