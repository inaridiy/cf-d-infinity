## Purpose and Context

D∞ (`cf-d-infinity`) は、Cloudflare Workers と Durable Objects の上の、水平に分割する SQLite 互換のデータベースである。
設計の全体は `docs/overview.md` (英語)、実装は `packages/cf-d-infinity/src/` にある。

この作業の目的は、利用者 (リポジトリの持ち主) の言葉で次のとおりである。

> 地固め、というのは今後のありとあらゆる拡張に耐えられる、堅牢な素地を作るという意味です。そして堅牢な素地が出来たとき、Early版として出せると思う

npm への公開は、素地ができるまで行わない。既知の欠陥を塞ぐことは目的ではない。

### なぜこの作業をしているか

2026-11-10 までに、独立のレビューを 3 回行った。毎回、同じ種類の欠陥 (誤った結果、確定したのに適用できない取引、止まるクラスタ) が新しく見つかり、
私 (この計画を書いているエージェント) は指摘を 1 件ずつ直した。直した修正が、次の回で新しい欠陥として見つかった。利用者はこの進め方を止めた。
原因は、守るべき条件を各所で手作業で守っていたこと、分からないときに黙って通していたこと、検査が欠陥のある掛け合わせを生成していなかったことである。

### 利用者が決めた規則 (変えてはいけない)

1. レビューや検査の指摘を、1 件ずつ直さない。指摘は不変条件とその持ち主 (下の表) に割り当てる。同じ場所の 2 回目の修正で手を止め、
   構造を変えるか、対応する範囲を削るかを提案する。
2. 修正の前に、それを見つける生成器か検査を用意する。見つけられなければ、検査のほうを広げる。
3. 仕組みを足す変更は機能として扱い、先にモデルを書く。
4. シャードをまたいだら失敗する、という挙動を作らない。行がどのシャードに載るかは利用者が決められないので、データ次第で失敗する構文は、
   構文ごと使えないのと同じである。1 シャードで扱えない文は、断るのではなく、行を集めて Worker の SQLite で実行する経路へ落とす。
   断ってよいのは、文の形や表定義だけで決まり、開発中に毎回失敗するものに限る。資源の上限 (集める行数、取引の大きさ) は例外で、文書に書く。
5. 取引の保証は serializable のまま出す。
6. 全体レビューによる欠陥探しを、これ以上しない。別のモデルには、計画への反論を頼む。

### 用語

- **span (範囲)**: 文が「読む」と宣言する行の集合。主キーの 1 行、shard key の値の全行、条件に合う行、表の全行の 4 種類。シャードは、範囲にある未決着の intent を決着させてから文を実行し、commit のときに、範囲が読んだ後で変わっていないかを検証する。
- **intent**: 2 相コミットで prepare 済み、未決着の書き込み。
- **行を集める経路 (gather)**: 走査を各シャードへ送り、行を Worker の中の SQLite (sql.js) に集め、元の文をそこで実行する。走査の文と範囲が同じ物 (`Scan`) から作られる。
- **wasmWrite**: 行を集めた Worker の SQLite で書き込みの文を実行し、捕捉した行の変更を、行を持つシャードへ振り分ける経路。
- **グローバル index**: シャードをまたぐ UNIQUE を守るための表 `__gidx_<名前>(k, pk, sk)`。行と同じ取引で保守する。

### 不変条件と持ち主

6 つを守っても残る種類が 3 つある (Codex の指摘)。

- 文の書き換えが意味を変える (例: `AVG` を `SUM` と `COUNT` に分けると、和があふれる)。受け持つのは、SQLite との差分テストと、文を再生する検査。
- 値が、検査に届く前に壊れる (例: Hrana 経由の 2^53 を超える整数)。入口で断る。未着手。
- 安全だが進まない (例: 16 MB を超えるグループは運べず、分割が終わらない)。不変条件 4 のモデルに、進行の条件として入れる。

### index

- 一意でない `CREATE INDEX` は、shard key を含まなくても、各シャードのローカル index である。書き込みは 1 シャードのまま。
- グローバル index は UNIQUE だけ。同じ列のローカル index (`__gidx_<名前>__rows`) も各シャードに作る。
- shard key でない列で引く読みは、いまは全シャードを読む。各シャードはローカル index で引く。
- **Early までにやること**: UNIQUE の列を等値で引く読みは、UNIQUE の index を引いて 1 シャードだけ読む。手順 (引く → 行を読む → 同じ時刻で引き直して確かめる) をモデルに入れてから実装する。
- 一意でない列を 2 シャードで引ける index (Vitess のように、書く順序で保守する対応表) は、後から別種の index として足す。

### 対応する範囲

次は、文の形や表定義だけで決まる理由で、`unsupported:` で断る。開発中に毎回失敗する。

- trigger、生成列、`CREATE TABLE ... AS SELECT`、`ALTER TABLE` の `RENAME COLUMN` と `DROP COLUMN`
- 主キー、shard key、シャードをまたぐ UNIQUE の列の、BINARY 以外の照合順序
- INSERT の `ON CONFLICT` や `RETURNING` の中のサブクエリ
- 1 回の DDL に複数の文

SQLite との差分テスト (`test/diff.ts`) と、文を再生する検査は、「SQLite と同じ答えか、`unsupported:` か」を合格にする。断った文は SQLite 側でも実行しない。

SQLite と結果が違ってよいもの: 行の物理的な並び順で結果が決まる文 (ORDER BY のない LIMIT、複数の行を同じ UNIQUE の値へ書き換える `UPDATE OR REPLACE` など)。

資源の上限 (規則 4 の例外): 1 文で集められるのは 20 万行、32 MB。1 取引が 1 シャードに書けるのは、変更前後の行を合わせて UTF-8 で 1 MB。

### 衝突を自分で解決する文

`INSERT OR IGNORE`、`OR REPLACE`、`REPLACE`、`ON CONFLICT` を、シャードをまたぐ UNIQUE のある表へ入れる文は、計画 `conflictInsert` になる。
衝突し得る行 (同じ主キー、同じ UNIQUE の値。別のシャードの行は UNIQUE の index を引いて場所を知る) を集め、元の文を Worker の SQLite で実行する。
ここまでは `6b55ad3` に入っていて、本物の SQLite との突き合わせ (`test/conflict-clauses.test.ts`) と、並行の再生の検査に通っている。

集めていない行と衝突したら、その行を集め足して実行し直す仕組み (`Txn.wasmWrite` の繰り返し) は、`45e9b57` (WIP) にある。未完成。

## Surprises & Discoveries

- 範囲の検査を既存の 404 件に掛けると、誤検出を除いて「UNIQUE のある表への書き込みが、同じ値を持つ別の行を読む」の 1 種類だけが出た。
  範囲を広げると、確定済みで適用待ちの取引が、次の書き込みの時点で決着され、書き込みは SQLite の本物の答えを受け取るようになった。
- 文を再生する検査は、入れた直後に、3 回のレビューで出ていなかった欠陥を 2 件見つけた。どちらも「いつ読んだか」の穴で、範囲の検査では見つからない。
- 2 件目は 16 回に 3 回ほどしか出なかった。シミュレータが決定的でないことが、原因の特定を遅らせた。
- `ON CONFLICT (email)` は、シャードの表に UNIQUE (email) がないので、衝突がなくても SQLite のエラーになっていた。利用者の指摘で分かった。
- 主キーに NULL のある行の取り違えと、`pragma_table_info('__txn')` でシャードの内部の表が読めることは、Codex の指摘を手元で再現した。
