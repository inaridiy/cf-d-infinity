# 地固めのやり直し (作業ノート)

開始: 2026-11-10。場所はすべてリポジトリの根からの相対パス。コマンドは `packages/cf-d-infinity` で実行する。

## 目的と完了の条件

目的は、今後のあらゆる拡張 (文の形、表定義の機能、復元、分岐、リージョン配置、運用の操作) に耐える、堅牢な素地を作ることである。
既知の欠陥を塞ぐことは目的ではない。素地ができたときに、Early 版として公開する (利用者の言葉、2026-11-10)。
「レビューが何も見つけなかった」を完了の条件にしない。

素地が堅牢であるとは、次のことを言う。

- 不変条件のそれぞれを、1 つの層が、文の形や機能によらない仕組みで守っている。新しい機能を足す人が、その条件を思い出して手で守る必要がない。
- 守れていないときは、黙って誤った結果になるのではなく、エラーになるか、検査が見つける (fail-closed)。
- 機能を足すときに何を確かめればよいかが、検査と生成器として用意されている。

完了の条件:

1. 過去の欠陥 (`Faults` の切り替えと、修正を戻したパッチ) を入れ直したとき、個別の回帰テストではなく生成器と検査 (下の「検出の道具」) が、重大なものを全部、全体の 9 割以上を、CI の時間内に見つける。
2. 拡張の試験に通る。切った機能を 1 つ、不変条件を意識せずに素朴に戻したとき、検査がその誤りを見つけるか、エラーになる。
3. 計画の種類 × スキーマ機能 × 障害の表が埋まり、夜間実行で 2 週間、新しい種類の失敗が出ない。
4. 範囲 (span) を作る関数と、キー文字列を作る関数が、それぞれ 1 つしかない。

対応範囲を切ることは、この目的に反しない。切った機能は、素地の上に、検査を通しながら戻す。

## 利用者の制約 (2026-11-10)

- レビューの指摘を 1 件ずつ直す進め方をやめる。指摘は不変条件とその持ち主に割り当てる。
- 同じ場所の 2 回目の修正で手を止め、構造の変更か、対応範囲の削減を提案する。
- 修正の前に、それを見つける生成器か検査を用意する。見つけられなければ、検査のほうを広げる。
- 仕組みを足す修正は機能として扱い、先にモデルを書く。
- 4 回目の全体レビュー (欠陥探し) はしない。Codex には、この計画への反論を頼む。

## なぜやり直すか

3 回のレビューが、毎回同じ種類の欠陥を見つけた。事実の一覧は、会話の中でまとめたものを `docs/roadmap.md` の末尾の節と `test/open/` の再現テストに残してある。原因は次のとおり。

- 不変条件を、各所で手作業で守っていた。分からないときに最も狭い主張をする作りだった (fail-open)。
- シャードは受け取った SQL をそのまま実行し、Worker が宣言した範囲に収まるかを確かめない。
- 適用 (phase 2) は失敗しない前提で、prepare は別のコードで失敗を予測していた。
- DDL と分割の順序を、状態を持たない Worker が進めていた。Meta は記録するだけだった。
- 並行のテストは点読み書きの文が 6 種類ほど、逐次のファザーは表定義が 1 つで、欠陥のある掛け合わせを生成していない。シミュレータは決定的でない (実時間のタイマー)。

## 不変条件と持ち主 (合意した設計)

| # | 不変条件 | 持ち主 | 仕組み |
|---|---|---|---|
| 1 | シャードで実行する文が読む範囲 ⊆ 宣言した範囲 | 範囲を作る関数 1 つ (Worker) と、決着させるシャード | 既定は「shard key の単位で全表」。テスト済みの規則がある形だけ狭める。読む表は Worker の SQLite でコンパイルして確かめ、合わなければ行を集める経路へ落とす |
| 2 | 確定した取引は適用できる | シャードの prepare | 本物の適用処理を、ほかの intent を載せた状態で試して巻き戻す。繰り返し失敗する取引は隔離する |
| 3 | 記録した DDL は、再生する場所すべてで実行できる | Meta | シャードの文と、Worker で再生する文の両方を、記録の前に実行して確かめる |
| 4 | 表定義の版と範囲の移動の順序が、全シャードで一致する | Meta | 分割の開始と終了を DDL と同じログに記録し、互いに開いている間は断る。先にモデルを書く |
| 5 | 内部の表は利用者の SQL から触れない | Worker のコンパイル | Worker の SQLite には利用者の表しかないので、内部の表を名指す文はコンパイルで落ちる |
| 6 | 行と shard key の同一性は 1 通り | 1 つのモジュール | キー文字列を作る唯一の関数にまとめ、SQLite の等値と総当たりで照合する |

範囲を広げて競合が増えすぎる場合は、範囲を手で狭めるのではなく、snapshot isolation へ下げることを検討する (未決定。計測してから決める)。

## alpha で切る範囲 (合意)

- 主キー、shard key、index の列の、BINARY 以外の照合順序
- 生成列、trigger、`CREATE TABLE AS`
- `RENAME COLUMN`、`DROP COLUMN`
- 行のある表への、データ次第で失敗する DDL (取り消しの仕組みも不要になる)
- グローバル index を読み書きの経路に使うこと (一意性の保証には残す)
- 分割と同時の DDL

README は「どの文も、SQLite と同じ答えを返すか、`unsupported` のエラーを返す」と約束する。

## 順序

1. 機能の追加と、3 回目の指摘への個別修正を凍結する。
2. 検出の道具を作る。見つかったものは不変条件ごとに仕分ける。
   - 範囲の検査: 宣言した範囲の外の行を消して同じ文を再実行し、結果を比べる
   - 適用と行イメージの往復の検査、キーの同一性の検査
   - 確定順の再生: 確定した取引を時刻順に 1 つの SQLite で再生して比べる。phase 2 の遅延を障害として入れる
   - 表定義の機能の一覧 × 小さな文法の総当たり (逐次の差分テスト)
   - シミュレータを決定的にする (タイマーを注入する)
3. 範囲を切る。
4. 不変条件を持ち主へ移す。DDL と分割は、Meta・DDL・分割を合わせたモデルを先に書く。
5. 慣らし運転。

まだやらないこと: 実行を自前で持つこと、CTE による範囲の強制を本番に入れること、実装からモデルへのトレース検証、復元と分析、性能の作業。

### 2026-11-10 範囲の検査と、範囲を作る関数の一本化 (ブランチ `foundation-3`)

- 範囲の検査を入れた (`src/shard/core.ts` の `checked` と `deleteOutside`、`ShardDeps.spanEscape`)。シミュレータでは既定で掛かり、`test/setup.ts` がどの試験でも結果を確かめる。検査そのものの試験は `test/span-check.test.ts`。
- 最初に掛けたとき、既存の 404 件のうち 10 件が引っかかった。誤検出は 2 種類 (`random()` を含む文、送った行数を数える試験) で、残りは全部「UNIQUE のある表への書き込みが、同じ値を持つ別の行を読む」だった。3 回目のレビューの指摘と同じ種類で、ほかの種類は出なかった。
- グローバル index を読み書きの経路に使うのをやめた (合意した削減)。`gidxRoute`、`wideSpans`、`late`/`clocked` が消えた。index の列で引く文は、全シャードへ条件を押し下げて集める。
- 範囲を作る関数を `src/client/spans.ts` の 1 か所にした。既定は「shard key の値ごとに、文が読む表の全行」。狭める規則は 2 つ (主キーの点読み、UNIQUE のない表への主キーの点書き)。文が読む表は Worker の SQLite のコンパイル結果で確かめ (`Db.tablesOf`)、プランナが知らない表を読む文は `unsupported` で断る。
- 結果: 全 415 件が検査を掛けた状態で通る。`test/open/` の「UNIQUE の読み」4 件は個別の修正なしで通ったので、`test/unique-reads.test.ts` へ移した。`x IN 表` を含む INSERT は、誤った値を入れる代わりに断るようになった。
- 過去の欠陥を戻す切り替え `spanFaults.rowSpanDespiteUnique` を入れた。戻すと検査が見つけることを `test/span-check.test.ts` で確かめている。

分かったこと:

- 範囲が広がった結果、確定済みで適用待ちの取引は、同じ shard key の値への次の書き込みが来た時点で決着される。その書き込みは、やり直しの要る「pending」ではなく、SQLite の本物の答え (UNIQUE 違反など) を受け取る。
- 費用は未計測。UNIQUE のある表では、同じ shard key の値 (テナント) への並行する取引が、別の行を書いていても commit で競合する。計測してから、狭める規則を足すか、snapshot isolation へ下げるかを決める。
- 範囲の検査が見つけられないもの: 送り先のシャードにない行を読むべきだった文 (行は別のシャードにある)。これは、表の集合の照合 (`tablesOf`) と、SQLite との差分テストの役目である。
- `test/open/backfill-resume.test.ts` は通るようになったが、直ったのではない。読みが index を使わなくなったので、index の項目が欠けていても読みの結果に現れないだけである。index の中身は欠け得る。UNIQUE の保証に効くので、未解決のまま扱う。

グローバル index を経路に戻すとき (利用者の質問、2026-11-10) に要るもの:

- 経路の規則を 1 つ足す。index のシャードと行のシャードを同じ時刻 T で読む手順 (引く、行を読む、同じ T で引き直して確かめる) を決め、モデルに入れる。
- 範囲は走査と同じ物から作る (`scanSpans`)。範囲の検査と差分テストが、その経路の文にもそのまま掛かる。
- 経路を戻すまでの緩和策: グローバル index と同じ列に、シャード内の index も作る。全シャードを読むことは変わらないが、各シャードは表を走査せずに index で引ける。

次にやること: 残りの削減 (照合順序のあるキー、生成列、trigger、CTAS、RENAME/DROP COLUMN、一意でないグローバル index をシャード内の index にする、backfill の途中経過の保存をやめる)、確定順の再生の検査、シミュレータを決定的にする、Meta・DDL・分割のモデル。

### 2026-11-10 削減を入れた (ブランチ `foundation-3`)

- 断るようにしたもの (エラーは `unsupported:` で始まる): 生成列、trigger、`CREATE TABLE ... AS SELECT`、`RENAME COLUMN`、`DROP COLUMN`、主キー・shard key・シャードをまたぐ UNIQUE の列の照合順序。
- SQLite との差分テスト (`test/diff.ts`) は、「同じ答えか、`unsupported` か」を合格にした。断った文は SQLite 側でも実行しない。
- 内部の名前の予約を、`__` で始まる名前の全部から、実際に使う名前と接頭辞だけに狭めた。移行の道具が使う `__new_<表名>` を作れるようにするためである (drizzle-kit がそう書くという記憶による。未確認)。内部の表を名指す文は、Worker の SQLite でコンパイルできないので断られる (`Db.tablesOf`)。
- index を埋める作業の途中経過の保存をやめた。毎回先頭から埋める。1 回の要求で埋めきれない表への UNIQUE index の後付けは、エラーになる。
- 合意した削減のうち、入れなかったもの: 「行のある表への、データ次第で失敗する DDL」。drizzle などは UNIQUE を `CREATE UNIQUE INDEX` として別の文で出すので、これを断ると移行の道具が使えない。取り消しの仕組みは残した。
- 全 409 件が通る。`test/open/` に残るのは、分割と DDL の順序の 2 件 (不変条件 4、Meta へ移す) だけである。

### 2026-11-10 利用者の判断: index での検索は、地固めの範囲に入れる

経路を切ったままにすると、shard key でない列の `CREATE INDEX` は、検索に効かないのに、書き込みを毎回シャードをまたぐ確定にする。
利用者は「地固めの段階から入れるべき」と判断した。私は、既存の試験の書き換えが多いという理由で、一意でない index をそのまま残すことを
利用者に伝えずに決めていた。これは誤りだった。

index での検索を、次の形で地固めに入れる。

- 引く、行を読む、確かめる、の手順を決め、モデルに入れてから実装する。index のシャードと行のシャードを同じ時刻で読む。
- 範囲は走査と同じ物から作る。範囲の検査と差分テストが、そのまま掛かる。
- それまでの間、一意でない index がシャードをまたぐ確定を起こすことは、README に明記する。
