## Purpose and Context

D∞ (`cf-d-infinity`) は、Cloudflare Workers と Durable Objects の上の、水平に分割する SQLite 互換のデータベースである。
設計の全体は `docs/overview.md` (英語)、実装は `packages/cf-d-infinity/src/` にある。

この作業の目的は、持ち主の言葉で次のとおりである。

> 地固め、というのは今後のありとあらゆる拡張に耐えられる、堅牢な素地を作るという意味です。そして堅牢な素地が出来たとき、Early版として出せると思う

npm への公開は、素地ができるまで行わない。
既知の欠陥を塞ぐことは目的ではない。

### なぜこの作業をしているか

2026-11-10 までに、独立のレビューを 3 回行った。
毎回、同じ種類の欠陥 (誤った結果、確定したのに適用できない取引、止まるクラスタ) が新しく見つかり、前の作業者は指摘を 1 件ずつ直した。
直した修正が、次の回で新しい欠陥として見つかった。
持ち主はこの進め方を止めた。
原因は 3 つあった。
守るべき条件を各所で手作業で守っていたこと、分からないときに黙って通していたこと、検査が欠陥のある掛け合わせを生成していなかったことである。

### 持ち主が決めた規則 (変えてはいけない)

1. レビューや検査の指摘を、1 件ずつ直さない。指摘は不変条件とその持ち主 (下の表) に割り当てる。同じ場所の 2 回目の修正で手を止め、構造を変えるか、対応する範囲を削るかを提案する。
2. 修正の前に、それを見つける生成器か検査を用意する。見つけられなければ、検査のほうを広げる。
3. 仕組みを足す変更は機能として扱い、先にモデルを書く。
4. シャードをまたいだら失敗する、という挙動を作らない。行がどのシャードに載るかは利用者が決められないので、データ次第で失敗する構文は、構文ごと使えないのと同じである。1 シャードで扱えない文は、断るのではなく、行を集めて Worker の SQLite で実行する経路へ落とす。断ってよいのは、文の形や表定義だけで決まり、開発中に毎回失敗するものに限る。資源の上限 (集める行数、取引の大きさ) は例外で、文書に書く。
5. 取引の保証は serializable のまま出す。
6. 全体レビューによる欠陥探しを、これ以上しない。別のモデルには、計画への反論を頼む。

規則 4 は Early 版にも例外なく掛かる。
持ち主は 2026-11-11 に、次のように念を押した。

> Shardを跨ぐと動かない、様な経路はユーザーから見て使えないので、Early版ですらナシで。

### 用語

- **span (範囲)**：文が「読む」と宣言する行の集合。主キーの 1 行、shard key の値の全行、条件に合う行、表の全行の 4 種類がある。シャードは、範囲にある未決着の intent を決着させてから文を実行し、commit のときに、範囲が読んだ後で変わっていないかを検証する。
- **intent**：2 相コミットで prepare 済み、未決着の書き込み。
- **基準経路**：文が読む表の行を、走査で各シャードから Worker の中の SQLite (sql.js) に集め、元の文をそこで実行する経路。読みは計画 `gather`、書き込みは計画 `wasmWrite` (捕捉した行の変更を、行を持つシャードへ振り分ける) がこれにあたる。走査の文と範囲は、同じ物 (`Scan`) から作る。
- **最適化の経路**：基準経路と同じ結果を、より少ない費用で返す経路。文を 1 シャードへそのまま送る (`shard`、`write`)、集約を分けて押し下げる (`partial`)、上位 N 件を押し下げる、取引を省く autocommit の書き込み (`execAuto`) がある。
- **グローバル index**：シャードをまたぐ UNIQUE を守るための表 `__gidx_<名前>(k, pk, sk)`。行と同じ取引で保守する。
- **決定的なシミュレータ**：同じ seed を与えると、RPC の配送の順序まで同じ実行になるシミュレータ。実時間、待ち、乱数、取引の ID を `Runtime` (`src/runtime.ts`) から取り、シミュレータは seed から決まる `VirtualRuntime` (`test/sim.ts`) を渡す。

- 作るときに決めた数のシャードで、SQLite と同じ結果を返す。行の置き場所で結果が変わらない (規則 4)。取引は直列化可能である (規則 5)。

### 実験的なもの (利用者が選んで有効にする。既知の問題を文書に書く)

### 値の型の作り直し (2026-11-12、済)

構造の変更として、次の形にした (手順 1 から 5 は済んだ。決めたことは Decision Log の 2026-11-12)。並行の仕組みではないので、Quint のモデルは書かない。確かめるのは、SQLite との突き合わせである。

1. 検査を先に作る (規則 2)。SQLite との差分テストに、INTEGER と REAL の引数と、`typeof` を入れる。基準の SQLite は `node:sqlite` で、INTEGER を BigInt、REAL を数で束縛する (sqld と同じ)。値と列の型の組を作って、キーの関数と SQLite が入れる値を突き合わせる生成器も作る。
2. 値の表現。JS の数のうち、整数でない数は REAL、整数の数は INTEGER とする。整数の値を持つ REAL だけを、印のついた値で表す。2^53 を超える INTEGER は、今どおり入口で断る。Hrana の `float` は、整数の値なら印をつける。`integer` は数のまま。D1 の API と Service Binding の数は、そのまま受け取る (整数なら INTEGER。D1 と同じ)。
3. 束縛の関数を 1 つにする。DO の SQLite は数を REAL として束縛するので、INTEGER の引数は、文の中の位置を字句で見つけて、整数に変える式で包む。sql.js は整数を INTEGER として束縛するので、印のついた REAL を REAL に変える式で包む。包む式は型の親和性を持たない形にする (`CAST` だけだと列と同じ親和性を持ち、比べ方が変わる)。どの形が親和性を持たないかは、SQLite で確かめてから決める。
4. 型を運ぶ読み。Worker がさらに計算に使う読み (基準経路で集める行、集約の部分) と、行イメージ (変更ログ、intent、範囲の移動) は、Worker かシャードが作る文なので、列ごとに型を読む (`typeof` か、SQLite の json の関数)。利用者へ返す結果では、整数の値の REAL を、今どおり Hrana の `integer` で返す。経路によらず同じなので規則 4 には当たらないが、sqld との違いとして文書に書く。
5. キーの関数を 1 つにする。値と列の型からキー文字列を作る関数を 1 つにし、SQLite の型の揃え方 (文字列を数にする文法、REAL を有効数字 15 桁の文字列にすること) を写す。
6. その後で、形式を固める (順番の 2)。

## 設計上の決定 (現在形)

### 基準経路と最適化の経路

SQL の実行経路を、基準経路と最適化の経路の 2 種類に分けて扱う。

基準経路は、対応する文のすべてを、行がどのシャードにあっても実行できる。
基準経路が断ってよいのは、文の形、値、表定義だけで決まる理由と、資源の上限だけである。

最適化の経路は、文の形と表定義で決まる規則に当てはまる文にだけ使う。
最適化の経路が、実行の途中で「1 シャードでは答えられない」と分かったら、`NeedsReference` を投げる。
受けるのは `runPlanned` (`src/client/db.ts`) だけで、同じ文を基準経路で計画し直して実行する。
切り替えは、この 1 か所にしかない。
`NeedsReference` を投げるのは、次の 4 つである。

- シャードへ送る前の確認 (`Db.tablesOf`) が、プランナの知らない表を見つけた (`x IN 表名` など)。
- 同じ確認が、読みの文の中に表定義の参照 (`sqlite_master`、PRAGMA の関数) を見つけた。
- シャードの SQLite が、複合 SELECT の項の数で文を断った。
- 1 シャードへ送った、衝突を自分で解決する文が、別のシャードの行と衝突した (`Txn.assertUnique`)。

書き込みの基準経路 (`Txn.wasmWrite`) は、次を繰り返す。

1. 集めた行で、文を Worker の SQLite で実行し、変更を捕捉する。
2. 変更後の行と、主キーか UNIQUE の値が同じで、まだ集めていない行を探す (`Txn.conflicting`)。同じ主キーの行、同じシャード内 UNIQUE の値の行、同じシャードをまたぐ UNIQUE の値の行 (index の表を引いて場所を知る) である。
3. なければ、変更を確定する。あれば、その行を集め足して、1 からやり直す。

集め足した行があれば、無視するか、置き換えるか、UNIQUE 違反にするかは、SQLite が本物の表と同じに決める。
探すための読みは、取引の読みとして範囲に記録されるので、後から同じ値の行が入れば、commit の検証が競合にする。
1 回ごとに集めた行が 1 つ以上増えるので、止まる。
止めるのは、集める行数の上限 (資源の上限) だけである。

基準経路は行ロックを取らない。
行ロックは中断を減らすための最適化で、取らなくても serializable は保たれる。
`BEGIN IMMEDIATE` の取引の中の文が基準経路に落ちると、その文の書き込みは、`COMMIT` で競合になり得る。

検査は 3 通りで流す (`vitest.config.ts`)。
SQLite と突き合わせる検査を、通常の実行 (`sim`)、基準経路だけの実行 (`reference-scans`)、基準経路だけで条件も押し下げない実行 (`reference-full`) に掛ける。
3 つが同じ答えなら、行がどのシャードにあるかで答えが変わる経路がないことになる。

この分け方は、規則 1 の「構造を変えるか、範囲を削るか」に、決まった手を 1 つ与える。
最適化の経路の同じ場所に 2 回目の修正が要るときは、その最適化を削って基準経路へ落とす。
結果は変わらず、費用が増え、資源の上限 (20 万行、32 MB) に当たりやすくなる。

- 安全だが進まない (例: 16 MB を超えるグループは運べず、分割が終わらない)。不変条件 4 のモデルに、進行の条件として入れる。

### 先に決めておく構造の変更

規則 1 は、同じ場所の 2 回目の修正で手を止めることを求める。
次の 2 か所は、すでに修正を重ねているので、次に何をするかを先に決めておく。

- 取引の読む時点 (`Txn.call`、`Txn.advance`、`Txn.refreshTo`)。2 件直した。未解決の問題 1 は 3 件目ではなかった (検査の誤りだった)。3 件目が出たら、直さない。取引が読む時点を先へ進める仕組みを削り、最初の読みの時点のまま読み続ける形にする案を、中断の割合の実測と一緒に持ち主へ出す。読む時点を進めるのは中断を減らすための最適化で、進めなくても serializable は保たれる (進められなかった取引は、いまも最初の時点のまま読み続ける)。
- 最適化の経路。上の「基準経路と最適化の経路」に書いたとおり、その最適化を削る。

### index

- 一意でない `CREATE INDEX` は、shard key を含まなくても、各シャードのローカル index である。書き込みは 1 シャードのまま。
- グローバル index は UNIQUE だけ。同じ列のローカル index (`__gidx_<名前>__rows`) も各シャードに作る。
- shard key でない列で引く読みは、いまは全シャードを読む。各シャードはローカル index で引く。
- Early までにやること: UNIQUE の列を等値で引く読みは、UNIQUE の index を引いて 1 シャードだけ読む。手順 (引く、行を読む、同じ時刻で引き直して確かめる) をモデルに入れてから実装する。これは最適化の経路の 1 つで、素地ができてから足す (Plan of Work の 7)。
- 一意でない列を 2 シャードで引ける index (Vitess のように、書く順序で保守する対応表) は、後から別種の index として足す。

### 対応する範囲

次は、表定義だけで決まる理由で、`unsupported:` で断る。

- TEMP の表、trigger、生成列、`ALTER TABLE` の `RENAME COLUMN` と `DROP COLUMN`
- 主キー、shard key、シャードをまたぐ UNIQUE の列の、BINARY 以外の照合順序

次は、文の形だけで決まる理由で断る。

- `CREATE TABLE ... AS SELECT`
- 書き込みの文の中の、表定義の参照 (`sqlite_master`、PRAGMA の関数)
- 取引の中の DDL
- 1 回の DDL に複数の文 (DDL の入口が断る。エラーは `unsupported:` で始まらない)

次は、文と値だけで決まる理由で断る。

- 主キーの列に NULL のある行を作る書き込み
- Hrana で引数として届く、2^53 を超える整数

どれも、行がどのシャードにあるかには依らない。
`unsupported:` を返す箇所の一覧は `test/refusals.test.ts` が固定している。
断る箇所を足すと、その試験が落ちる。

以前は断っていた次の文は、基準経路で実行する。

- 衝突する行が別のシャードにある `UPDATE OR IGNORE` と `UPDATE OR REPLACE` (行の配置で断っていた。規則 4 に反していた)
- シャードをまたぐ UNIQUE のある表への、衝突を自分で解決する INSERT で、DEFAULT のある UNIQUE の列を省いたもの
- `x IN 表名` のように、FROM に現れない表を読む文
- INSERT の `ON CONFLICT` や `RETURNING` の中のサブクエリ

SQLite との差分テスト (`test/diff.ts`) と、文を再生する検査は、「SQLite と同じ答えか、`unsupported:` か」を合格にする。
断った文は SQLite 側でも実行しない。

SQLite と結果が違ってよいのは、行の物理的な並び順で結果が決まる文である (ORDER BY のない LIMIT、複数の行を同じ UNIQUE の値へ書き換える `UPDATE OR REPLACE` など)。

資源の上限 (規則 4 の例外) は次のとおりである。
1 文で集められるのは 20 万行、32 MB。
1 取引が 1 シャードに書けるのは、変更前後の行を合わせて UTF-8 で 1 MB。

### 衝突を自分で解決する文

`INSERT OR IGNORE`、`OR REPLACE`、`REPLACE`、`ON CONFLICT`、`UPDATE OR IGNORE`、`UPDATE OR REPLACE` は、衝突する行がどのシャードにあっても、SQLite と同じ結果になる。

シャードをまたぐ UNIQUE のある表への INSERT は、最初から基準経路で実行する。
それ以外は、1 シャードへ送る。
送った先で、別のシャードの行との衝突が見つかったら、基準経路で実行し直す。
衝突を解決するのは、どちらの場合も SQLite である。

本物の SQLite との突き合わせは `test/conflict-clauses.test.ts` と `test/refusals.test.ts`、並行の下での確認は文を再生する検査である。

   原因は、index の項目の消し方にある。
   シャードをまたぐ UNIQUE の index の表は、値 k を主キーにした 1 行で、どの行がその値を持つか (pk) を覚える。
   行が値 k を手放すと、Worker は「k の項目を消す」変更を出す。この変更は、項目がどの行のものかを確かめない。
   index が出来上がっていれば、k の項目は必ずその行のものなので、これで正しい。
   index を作っている最中 (既存の行の項目を埋めている間) は違う。まだ項目のない行 Y が値 k を持っているとき、別の行 X が k を取れる (Y の項目がないので、重複に気付けない)。そこで Y が k を手放すと、X の項目が消える。

### 6. モデルを先に書く仕事

#### 6 の前半: UNIQUE の index を、書き込みを止めて作る (不変条件 7。2026-11-11 に済。以下は決めたときの記録)

行のある表への `CREATE UNIQUE INDEX` (shard key を含まないもの) を、次の形に作り直す。

- index を記録する版が、その表を「書き込み禁止」にする。禁止は、表定義の一部としてシャードへ届く。
- シャードは、自分の持つ表定義を見て、その表への書き込みを断る。断る場所は、どの書き込みも通る 1 か所 (`assertWriteSetFits`。`prepareSync`、`commitLocal`、`execAuto`、`execDirect` が呼ぶ) にする。Worker も断るが、それは早く失敗させるためで、守っているのはシャードである。
- いまある仕組みを使う。シャードは、古い表定義の版の要求を断り、DDL を適用する前に、持っている intent を全部決着させる。既存の行を埋める処理は、全シャードがその版を適用した後で始まる。だから、埋める処理が始まった後は、その表への書き込みは、どのシャードでも確定しない。
- 埋める処理は、止まっている行を読んで、項目を書く。重複があれば、それは本物の重複なので、DDL を取り消して、UNIQUE 違反を返す。
- Worker の SQLite に index を作るのは、index が出来上がってからにする。
- 終わり方は 2 つで、どちらか 1 つだけが起きる。出来上がって公開するか、取り消すかである。index を作る処理が途中で止まったときのために、期限を持たせる。期限が過ぎたら取り消す。誰が取り消すか (Meta か、期限の過ぎた禁止に当たった Worker か) は、モデルで決める。「同じ文を出し直すと続きから埋める」処理は消す。
- index を作っている間は、分割を始めない。分割の途中は、index を作り始めない。これは不変条件 4 の「保守の操作は同時に 1 つ。Meta が許可する」の最初の使い道なので、その枠を、ここで作る。
- 書き込みを断るエラーは、やり直せるエラーにする (`unsupported:` ではない)。行の配置には依らない。取引の外の文は、Worker の中で、決まった時間まで待ってやり直す。資源の上限と並べて、文書に書く。

消せるもの: index を作っている最中の項目の保守、`Txn.assume` (呼んでいるのは、埋める処理だけ)、埋める処理の検証とやり直し、続きから埋める処理、BUG-2 と BUG-2b の種類。

モデルで先に確かめること。

- index を、実装と同じに「値から行への対応」で持ち、項目は値で消す。
- いまの設計 (作りながら書く) の版で、seed 364 の形 (2 行で足りる) の反例が出る。
- 禁止を Worker だけが確かめる版、intent を決着させない版、公開を版に結び付けない版で、反例が出る。
- 直した設計で、次が成り立つ。禁止されている表への書き込みは確定しない。確定した結果は、出来上がっていない index に依っていない。終わり方は 1 つである。
- 期限が公平に働けば、禁止は必ず解ける。

検査のほうで足すこと。

- DDL と並行する取引の検査は、いま、どの操作の UNIQUE 違反も「起きてよいもの」として受け入れている。種類を分ける。読みが UNIQUE 違反で失敗するのは、違反である。
- 作業負荷に、衝突を自分で解決する文と、行を集める読みを足す。この検査を、基準経路だけの実行にも掛ける。

### 8. 仕上げ

文書の全面の更新、実際の移行の道具 (drizzle-kit など) が出す文での確認、UNIQUE のある表での競合と費用の計測、慣らし運転。

- (2026-11-12) 値の型。JS の数のうち整数は INTEGER、整数でない数は REAL とし、整数の値の REAL だけを `{ real }` の印で表す (`src/value.ts`)。BigInt で INTEGER を表す案は採らなかった。DO の SQLite が BigInt を束縛できず、整数の値の REAL を表す手段がどちらにしても要るからである。束縛は Backend の 1 か所 (`bindTyped`) で、INTEGER の引数を `(CAST(? AS INTEGER)+0)` に包む。`CAST` だけだと式が列と同じ型の親和性を持ち、`'05' = ...` の比べ方が変わる。`+0` は親和性を消す (node:sqlite で比べ方、typeof、文字列への変換を確かめた)。文を字句で調べる費用は、包んだ文を型の並びごとに覚えて (512 件) 抑える。結果の数の型は運ばない (DO の SQLite が読み出しで区別しないので、利用者の文の結果の列ごとに typeof を足す費用がかかる)。型のない列の行イメージと、Worker が計算し直す読み (集める走査、集約の部分) だけ typeof を読む。並行の仕組みではないので Quint のモデルは書かず、SQLite との突き合わせ (`test/typed-diff.test.ts`) で確かめた。
- (2026-11-12) trigger が変更を捕まえるときのキー (`keySql`) は、REAL を `quote()` で書く。SQLite の JSON と printf は 15 桁か 16 桁で丸め、Worker のキーとずれる (基準経路だけの実行の `typed-diff` が見つけた)。`quote()` は、node:sqlite、workerd、sql.js のどれでも元の double に戻せる桁数で書く。

- (2026-11-12) モデルにある危ない順序は、乱択に任せず、モデルの反例をシミュレータの手順に写して確かめる。`finishWithoutClock` は、M5b が反例を出せるのに、history の乱択は 1000 seed に 1 回 (値の型の作り直しの後は 0 回) しかその順序を作れなかった。設計の穴はモデルが、実装がその順序で正しく動くかは写した手順が受け持つ。持ち主の問い (「乱択テストの前に、モデル検査出来たりはしないの？」) への答えとして決めた。SQLite の意味 (値の型など) は、モデルではなく本物の SQLite との突き合わせが受け持つ。
