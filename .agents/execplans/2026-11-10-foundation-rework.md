# 地固めのやり直し (作業ノート)

開始: 2026-11-10。場所はすべてリポジトリの根からの相対パス。コマンドは `packages/cf-d-infinity` で実行する。

## 目的と完了の条件

目的は、今後のあらゆる拡張 (文の形、表定義の機能、復元、分岐、リージョン配置、運用の操作) に耐える、堅牢な素地を作ることである。
既知の欠陥を塞ぐことは目的ではない。素地ができたときに、Early 版として公開する (利用者の言葉、2026-11-10)。
「レビューが何も見つけなかった」を完了の条件にしない。

素地が堅牢であるとは、次のことを言う。

- 不変条件のそれぞれを、1 つの層が、文の形や機能によらない仕組みで守っている。新しい機能を足す人が、その条件を思い出して手で守る必要がない。
- 守れていないときは、黙って誤った結果になるのではなく、エラーになるか、検査が見つける (fail-closed)。
- 機能を足すときに何を確かめればよいかが、検査と生成器として用意されている。

完了の条件:

1. 過去の欠陥 (`Faults` の切り替えと、修正を戻したパッチ) を入れ直したとき、個別の回帰テストではなく生成器と検査 (下の「検出の道具」) が、重大なものを全部、全体の 9 割以上を、CI の時間内に見つける。
2. 拡張の試験に通る。切った機能を 1 つ、不変条件を意識せずに素朴に戻したとき、検査がその誤りを見つけるか、エラーになる。
3. 計画の種類 × スキーマ機能 × 障害の表が埋まり、夜間実行で 2 週間、新しい種類の失敗が出ない。
4. 範囲 (span) を作る関数と、キー文字列を作る関数が、それぞれ 1 つしかない。

対応範囲を切ることは、この目的に反しない。切った機能は、素地の上に、検査を通しながら戻す。

## 利用者の制約 (2026-11-10)

- レビューの指摘を 1 件ずつ直す進め方をやめる。指摘は不変条件とその持ち主に割り当てる。
- 同じ場所の 2 回目の修正で手を止め、構造の変更か、対応範囲の削減を提案する。
- 修正の前に、それを見つける生成器か検査を用意する。見つけられなければ、検査のほうを広げる。
- 仕組みを足す修正は機能として扱い、先にモデルを書く。
- 4 回目の全体レビュー (欠陥探し) はしない。Codex には、この計画への反論を頼む。

## なぜやり直すか

3 回のレビューが、毎回同じ種類の欠陥を見つけた。事実の一覧は、会話の中でまとめたものを `docs/roadmap.md` の末尾の節と `test/open/` の再現テストに残してある。原因は次のとおり。

- 不変条件を、各所で手作業で守っていた。分からないときに最も狭い主張をする作りだった (fail-open)。
- シャードは受け取った SQL をそのまま実行し、Worker が宣言した範囲に収まるかを確かめない。
- 適用 (phase 2) は失敗しない前提で、prepare は別のコードで失敗を予測していた。
- DDL と分割の順序を、状態を持たない Worker が進めていた。Meta は記録するだけだった。
- 並行のテストは点読み書きの文が 6 種類ほど、逐次のファザーは表定義が 1 つで、欠陥のある掛け合わせを生成していない。シミュレータは決定的でない (実時間のタイマー)。

## 不変条件と持ち主 (合意した設計)

| # | 不変条件 | 持ち主 | 仕組み |
|---|---|---|---|
| 1 | シャードで実行する文が読む範囲 ⊆ 宣言した範囲 | 範囲を作る関数 1 つ (Worker) と、決着させるシャード | 既定は「shard key の単位で全表」。テスト済みの規則がある形だけ狭める。読む表は Worker の SQLite でコンパイルして確かめ、合わなければ行を集める経路へ落とす |
| 2 | 確定した取引は適用できる | シャードの prepare | 本物の適用処理を、ほかの intent を載せた状態で試して巻き戻す。繰り返し失敗する取引は隔離する |
| 3 | 記録した DDL は、再生する場所すべてで実行できる | Meta | シャードの文と、Worker で再生する文の両方を、記録の前に実行して確かめる |
| 4 | 表定義の版と範囲の移動の順序が、全シャードで一致する | Meta | 分割の開始と終了を DDL と同じログに記録し、互いに開いている間は断る。先にモデルを書く |
| 5 | 内部の表は利用者の SQL から触れない | Worker のコンパイル | Worker の SQLite には利用者の表しかないので、内部の表を名指す文はコンパイルで落ちる |
| 6 | 行と shard key の同一性は 1 通り | 1 つのモジュール | キー文字列を作る唯一の関数にまとめ、SQLite の等値と総当たりで照合する |

範囲を広げて競合が増えすぎる場合は、範囲を手で狭めるのではなく、snapshot isolation へ下げることを検討する (未決定。計測してから決める)。

## alpha で切る範囲 (合意)

- 主キー、shard key、index の列の、BINARY 以外の照合順序
- 生成列、trigger、`CREATE TABLE AS`
- `RENAME COLUMN`、`DROP COLUMN`
- 行のある表への、データ次第で失敗する DDL (取り消しの仕組みも不要になる)
- グローバル index を読み書きの経路に使うこと (一意性の保証には残す)
- 分割と同時の DDL

README は「どの文も、SQLite と同じ答えを返すか、`unsupported` のエラーを返す」と約束する。

## 順序

1. 機能の追加と、3 回目の指摘への個別修正を凍結する。
2. 検出の道具を作る。見つかったものは不変条件ごとに仕分ける。
   - 範囲の検査: 宣言した範囲の外の行を消して同じ文を再実行し、結果を比べる
   - 適用と行イメージの往復の検査、キーの同一性の検査
   - 確定順の再生: 確定した取引を時刻順に 1 つの SQLite で再生して比べる。phase 2 の遅延を障害として入れる
   - 表定義の機能の一覧 × 小さな文法の総当たり (逐次の差分テスト)
   - シミュレータを決定的にする (タイマーを注入する)
3. 範囲を切る。
4. 不変条件を持ち主へ移す。DDL と分割は、Meta・DDL・分割を合わせたモデルを先に書く。
5. 慣らし運転。

まだやらないこと: 実行を自前で持つこと、CTE による範囲の強制を本番に入れること、実装からモデルへのトレース検証、復元と分析、性能の作業。

### 2026-11-10 利用者の判断: index での検索は、地固めの範囲に入れる

経路を切ったままにすると、shard key でない列の `CREATE INDEX` は、検索に効かないのに、書き込みを毎回シャードをまたぐ確定にする。
利用者は「地固めの段階から入れるべき」と判断した。私は、既存の試験の書き換えが多いという理由で、一意でない index をそのまま残すことを
利用者に伝えずに決めていた。これは誤りだった。

index での検索を、次の形で地固めに入れる。

- 引く、行を読む、確かめる、の手順を決め、モデルに入れてから実装する。index のシャードと行のシャードを同じ時刻で読む。
- 範囲は走査と同じ物から作る。範囲の検査と差分テストが、そのまま掛かる。
- それまでの間、一意でない index がシャードをまたぐ確定を起こすことは、README に明記する。

### 2026-11-10 index の設計を決め直した (利用者の指示)

利用者の指示: 「動くが SQLite と違う」ものの一覧のうち、index の 2 点 (shard key でない列の検索が全シャードを読む、
一意でない index が検索に効かないのに書き込みを重くする) は Early の時点で解決する。残りは、後から足しにくいかどうかで判断する。

分散 SQL の系統を並べると、D∞ は「単体のエンジンをシャードに並べる」系統 (Citus、Vitess、Aurora Limitless、MongoDB) にいる。
この系統の標準は、各シャードのローカル index と、全シャードへの並列の問い合わせである。全体の index を取引で同期して保守するのは、
またぐ確定が安く、全体で MVCC を持つ系統 (Spanner、CockroachDB、TiDB) のやり方で、Durable Object にはその前提がない。

決めたこと:

- 一意でない `CREATE INDEX` は、shard key を含まなくても、各シャードのローカル index にする。書き込みは 1 シャードのまま。
- グローバル index (`__gidx_*`) は UNIQUE だけにする。UNIQUE の列と同じ列のローカル index も各シャードに作り、行のシャードが index で引けるようにする。
- UNIQUE の列を等値で引く読みは、UNIQUE の index を引いて、行のあるシャードだけを走査する。走査は行を集める経路 (`scanSpans`) をそのまま使う。
  手順: index を引く (T0) → 行のシャードを、T0 以上の、そのシャードの最新の時刻 Ts で読む → index を Ts で引き直し、同じ結果なら確定。
  違えば全体をやり直し、数回で駄目なら全シャードの走査に落とす。取引の中で T が決まっていれば、その T で 2 回読むだけでよい。
  モデルに入れてから実装する。
- 一意でない列を 2 シャードで引ける全体の index (Vitess のように、書く順序で保守する対応表) は、後から別種の index として足す。

後から変えにくいので、いま決めるもの: 取引の保証 (serializable のまま)、UNIQUE のある表での競合の増加を戻すこと
(範囲を「名指しした行と、同じ UNIQUE の値の行」に狭める規則を足し、計測する)、`CREATE INDEX` の意味、公開 API と設定名と行の置き方。

後から足せるので、Early では制限として明記するもの: 全シャードを読む読み、またぐ取引の遅さ、古いスナップショットの失敗、
1 取引 1 MB、行の多い表への UNIQUE の後付け、復元・統合・分割の取り消し、切った機能 (trigger、生成列、RENAME/DROP COLUMN、照合順序つきキー)。

順序: (1) 一意でない index のローカル化、(2) UNIQUE の範囲の規則と計測、(3) UNIQUE 経由の読みのモデルと実装。

### 2026-11-10 index のローカル化と、UNIQUE の範囲の規則 (ブランチ `foundation-3`)

- 一意でない `CREATE INDEX` を、各シャードのローカル index にした。index の表も、書き込みのシャードをまたぐ確定もない
  (`test/basic.test.ts` が、書き込みで prepare が出ないことを確かめる)。シャードをまたぐ UNIQUE には、行の表にも同じ列のローカル index を作る。
- シャードをまたぐ index の手順の試験 (`test/ddl-concurrent.test.ts`) は、UNIQUE の index に付け替え、index の中身を直接照合するようにした。
  経路を切ってから、読みの結果だけを見る試験は index の中身を確かめなくなっていた。欠陥を戻して照合が見つけることも確かめている (BUG-3 put back)。
- 範囲の規則 3 を足した (`src/client/spans.ts`)。UNIQUE のある表への 1 行の書き込みは、名指しした行と、UNIQUE の検査で読む行だけを範囲にする。
  DELETE と、UNIQUE の列に触らない UPDATE は、名指しした行だけ。値が定数で決まる INSERT は、その値を持つ行を条件の範囲にする。
  値が決まらない形 (式の値、UNIQUE の列を書く UPDATE、UPSERT、条件付きの UNIQUE がある表の UPDATE) は、shard key の値の全行のまま。
- 結果: 同じテナントの別の行を、別の UNIQUE の値で書く取引は、互いに競合せずに両方 commit する。同じ値を入れる取引は片方だけが通る
  (`test/unique-conflicts.test.ts`)。範囲の検査を掛けた状態で全 413 件が通る。
- 競合の頻度を負荷を掛けて測ることは、まだしていない。

次にやること: UNIQUE の列を引く読みの手順をモデルに入れ、実装する (太字の残り)。その後、確定順の再生の検査、シミュレータの決定化、
Meta・DDL・分割のモデル、切った機能のために残っている使われないコード (生成列、trigger、CTAS、照合順序の畳み込み、一意でないグローバル index) の削除。

### 2026-11-10 Codex による計画への反論 (別のモデルによる方向の点検)

依頼は「欠陥探しではなく、この計画が弱いところへの反論」。報告の全文は `.agents/execplans/evidence/2026-11-10-codex-direction-pass.md`。
Codex は `foundation-3` の 51032ed を読み、型検査と範囲の検査の試験を実行した。挙げた例は、断りのないかぎりコードを読んでの指摘である。

採り入れること:

- 6 つの不変条件を全部守っても残る種類が 3 つある。計画に足す。
  - 文の書き換えが意味を変える。例: `AVG` をシャード側の `SUM` と `COUNT` に分けると、SQLite なら答えが出る入力で整数の和があふれる。
    範囲は正しくても結果が違う。持ち主は、行を集める経路の「元の文をそのまま実行する」既定と、SQLite との差分テスト。書き換える最適化は、差分テストを通した形だけにする。
  - 値が、検査に届く前に壊れる。例: Hrana の整数の文字列が JavaScript の数値になり、2^53 を超える値が変わる。入口で断る (黙って丸めない)。
  - 安全だが進まない。例: 16 MB を超える shard key のグループは運べないので、分割が終わらず、Meta が DDL を分割の後ろに並べると DDL も永久に待つ。
    再構成のモデルに、進行の条件 (何が保守の枠を解放するか) を入れる。運べないグループは、所有権を切り替える前に断るか、分割して運ぶ。
- 不変条件 1: 表の集合の照合は、行が送り先のシャードにあること (経路の完全さ) を確かめない。走査の文、送り先、範囲を、1 つの計画の物から作る形を、
  利用者の文をそのまま送る経路にも広げる。それができない形は、行を集めるか、断る。「範囲を作る関数が 1 つ」は、この性質の証明にならない。
- 不変条件 2: 適用の試行の前に、SQL だけを触る同期の適用の核を切り出す。いまの `applyAndLog` は `maxCommit` や直近の書き込みの索引も書き換えるので、
  巻き戻しても戻らない。試行が通った後で容量が尽きる場合があるので、余裕を見た受け入れの上限も要る。隔離は、確定の事実を残し、捨てない。
- 不変条件 3: 空の表での検証は、行のある表への適用を保証しない。「記録した操作の試み」と「公開された表定義」を分けて書く。取り消しの仕組みは残す (既に残した)。
- 不変条件 4: 共有のログだけでは足りない。保守の操作に ID と世代を持たせ、遅れて届く fence や切り替えを、その操作のものとして確かめる。
  最初は、同時に 1 つの保守の操作だけを許す。実行は Autoscaler のままでよく、Meta は許可と締め出しを持つ。
- 不変条件 5: コンパイルが通ることは、許可ではない。`sqlite_master` や `pragma_table_info('__txn')` は Worker の SQLite でもコンパイルでき、
  シャードでは内部の表について答える (再現した)。メタデータを読む式は Worker の SQLite でだけ実行し、シャードへ送る文の中では断る。
- 不変条件 6: 行の同一性と shard key の同値は別の性質である。INTEGER でない主キーは NULL を複数持てるので、主キーの値では行を区別できない (再現した)。
  alpha では、宣言した主キーの値に NULL を持つ書き込みを断る。数値の範囲 (2^53) も、ここで決める。
- 検出の道具は、生成器がないと偽の安心になる。
  - 範囲の検査: 範囲の外の行を全部消すと、打ち消し合う依存を見逃す。行がないと、あるはずの行への依存も見えない。3,000 行を超えると省いている。
    範囲の中が同じで外が違う状態の組を生成し、検査した数と省いた数を報告する。
  - 確定順の再生: 行イメージを再生するだけでは、内部の一貫性しか確かめない。元の文、引数、途中の観測、要求と応答の順序を記録して、文を再生する。
  - 決定的なスケジューラ: 決定的であることと、基盤に忠実であることは別。確定前の書き込みの消失、出力の締め切り、alarm、再起動、混在する版を制御する。
  - SQL の生成と並行の生成を掛け合わせる。別々に回しても、交わるところを見逃す。
- 完了の条件を測れる形にする。安全性の違反が 0、対応する形ごとの成功した実行の下限 (断れば合格、で空になるのを防ぐ)、障害が止んだ後の回復の上限、
  説明のつかない拒否と中断の割合の上限。差分テストは、受け付けた文の割合を記録し、断った文が状態を変えていないことも確かめる。
- 順序: 独立した再生の検査と、決定的なスケジューラを、UNIQUE の列を引く読みの経路より先に作る。
- 移行の道具との相性は、実際に生成された移行の文で確かめて決める。取引の中の DDL は、いまは断っている。

採り入れないこと、保留:

- 行のある表への DDL に書き込みの締め出しを使う案は保留。取り消しの仕組みは独立の検証で健全とされているので、当面はそれを使う。
- snapshot isolation を逃げ道にしない点は、Codex も同じ意見で、既に決めたとおり。

順序の見直し (上の「次にやること」を置き換える):

1. 文を再生する差分の検査 (元の文と引数を記録し、1 つの SQLite で再生する) と、受け付けた割合の記録。
2. シミュレータを決定的にし、確定前の書き込みの消失と再起動を制御できるようにする。
3. 入口の受け入れの規則: 2^53 を超える整数、主キーの NULL、シャードへ送る文の中のメタデータの参照。
4. UNIQUE の列を引く読みの経路 (モデルを書いてから)。
5. 適用の核の切り出しと、prepare での試行。
6. 再構成のモデル (Meta、DDL、分割、操作の ID と世代、進行の条件) と、Meta への移動。
7. 使われなくなったコードの削除、実際の移行の文での確認、慣らし運転。
